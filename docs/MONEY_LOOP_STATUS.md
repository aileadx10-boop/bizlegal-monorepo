## Fleet-wide findings

**F1 — Hub card checkout never captures money (critical).** **FIXED 2026-09-01.** Capture-on-return route `apps/hub/app/payment/paypal/return/route.ts` captures via `lib/payments/paypal-capture.ts` (idempotent, token-bound) before redirecting to `/payment/success`; the webhook now grants only on `PAYMENT.CAPTURE.COMPLETED` and defensively captures on `CHECKOUT.ORDER.APPROVED`; `createPayPalOrder` (`packages/payment/src/index.ts`) return_url now points at the capture route. Historical record: both hub card paths created PayPal orders with `intent:'CAPTURE'` and nothing ever called the capture endpoint:
- `/api/payments/paypal/start` one-time branch (`apps/hub/app/api/payments/paypal/start/route.ts`) — return_url `/payment/paypal/return` previously had **no page**.
- `/api/pay/start` card → `startCheckout` → `createPayPalOrder` — return_url previously `/payment/success`, whose page renders status text and captures nothing.
- The only capture calls in hub were TRACR-specific (`apps/hub/app/api/tracr/paypal-capture/route.ts:59`).
- The hub PayPal webhook used to map `CHECKOUT.ORDER.APPROVED` → `status='active'` and fire `payment.confirmed` + entitlement grants + confirmation email — i.e. it granted fulfillment on an **approval that was never captured**.
- Consistent with `AgentCheckoutButton` showing "Card payments temporarily unavailable — crypto only" (`apps/hub/app/components/ui-v2/AgentCheckoutButton.tsx:188`) — but `/checkout` and `/api/pay/start` still expose card.

**F2 — Client-controlled amounts on the generic checkout.** **FIXED 2026-09-01.** `apps/hub/lib/payments/price-map.ts` is now the server-side price map; `/api/payments/{paypal,nowpayments,wire}/start` resolve the amount from (product, tier, interval) and reject unknown SKUs or mismatched client amounts; the `/checkout` page resolves the displayed price via `/api/payments/price`. Historical record: `/checkout?amount=<cents>` was taken from the URL and forwarded as `amount_cents` to the start routes with only a range check, so any tier could be bought for $0.50 by editing the query string.

**F3 — Subscription 503 matrix (the known defect, mapped).** Pattern: `PAYPAL_PLAN_ID_${PRODUCT}_${TIER}_${INTERVAL}` lookup, 503 when unset (`apps/hub/app/api/payments/paypal/start/route.ts:57-60,166-175`; identical copies in `apps/tracr`, `apps/brai`, `apps/lexaudit`, `apps/docai/web` `…/api/payments/paypal/start/route.ts:56-59,163-172`; coguard variant uses the full product_id as key, `apps/coguard/app/api/payments/paypal/start/route.ts:61-66`). Because every subdomain pricing page routes to **hub's** `/checkout`, the plan IDs that matter are hub's env. Cross-referencing pricing-page CTAs vs vault names:
- Present in vault: `HUB_PRO_*`, `HUB_SCALE_*`, `CONDUCTOR_{TEAM,FIRM}_{MONTHLY,YEARLY}`, `DOCAI_{TEAM,FIRM}_MONTHLY`, `LEXAUDIT_{BOUTIQUE,MIDMARKET}_{MONTHLY,YEARLY}`, `LEXAUDIT_MONITOR_MONTHLY`, `COGUARD_{SOLO,LITIGATION}_MONTHLY`, `MONITOR`, `RETAINER`.
- **Missing → card subscription 503s:** all `TRACR_*` (tracr sells monthly/yearly at every tier), all `BRAI_*`, `LEXAUDIT_SOLO_*`, `DOCAI_STARTER_*`, `DOCAI_*_YEARLY`, `CONDUCTOR_SOLO_*`, `COGUARD_*_YEARLY`.
- Note also: tracr is "mid-fix" in the working tree (uncommitted `lib/tiers.ts` consolidation removing the crypto/fiat price split); the 503 defect on its pricing-page subscriptions is **not** addressed by that fix, because those buttons route to hub.

**F4 — Hub fulfillment gap for cross-app products.** Hub webhooks grant only conductor / casp-bundle / ai-policy / ofac-watch (`apps/hub/app/api/payments/paypal/webhook/route.ts:255-258`; `apps/hub/app/api/payments/nowpayments/webhook/route.ts:236-243`). Everything else bought via hub checkout — tracr, brai, forge, docai tiers, lexaudit monitor, bench — receives `sendPaymentConfirmationEmail` and nothing else. Even the crypto rail (which does collect money) delivers no product for those SKUs. TRACR bought via hub is doubly broken: hub collects no wallet address, so no report could be generated anyway.

**F5 — "Subscriptions" via `/api/pay/start` are one-time charges.** `packages/payment/src/index.ts:296-299` deliberately avoids the PayPal Subscriptions API; a `monthly` product on the card path creates a single Orders-API payment that never recurs. Affects `bench_managed_monthly` ($5,000/mo → collected once) and any registry monthly sold card-first.

**F6 — Webhook verification fail-open spots.** `apps/tracr/lib/paypal.ts:98-99` returns `true` when `PAYPAL_WEBHOOK_ID` is unset; forge/tracr/brai NOWPayments handlers verify only `if (secret && sig)` (e.g. `apps/forge/apps/web/app/api/payment/webhook/route.ts:18`) — unset secret = unverified IPNs accepted. Hub fixed this class already (`apps/hub/app/api/payments/paypal/webhook/route.ts:53-58`). All named secrets exist in the vault; risk materializes only if a Vercel project is missing them.

**F7 — Env-name gaps vs vault (names only).** `NEXT_PUBLIC_PAYPAL_SCAN_ENABLED` (docai card-scan gate), `PAYPAL_COGUARD_WEBHOOK_ID` (falls back to shared ID), `BANK_EUR_*`/`BANK_USD_*` (hub wire instructions, `apps/hub/lib/payments/wire.ts`), `TRACR_BLOCKSCOUT_API_KEY`, `TRACR_ETHERSCAN_API_KEY` (optional), plus the plan-ID list in F3. `node scripts/audit-vault.mjs` currently reports 61 repo-wide missing names (many are services/scripts out of payment scope; payment-relevant ones listed here).

8. **Vault hygiene (F7).** Append `NEXT_PUBLIC_PAYPAL_SCAN_ENABLED`, `PAYPAL_COGUARD_WEBHOOK_ID`, `BANK_*`, and any new plan IDs to the vault; verify the same names are set in each Vercel project (not verifiable from code).
